# Структура проекта PDF-форм

## 1. Принцип организации

Каждая форма размещается в отдельном подпроекте внутри `forms/` и содержит свои промпты, документацию, редактируемые исходники и выпуски PDF. Новые формы создаются по одинаковой структуре и не требуют изменения существующих подпроектов.

На верхнем уровне хранятся каталог форм, общие промпты и документация проекта. Общие шаблоны и ресурсы добавляются по мере появления повторного использования. Такая организация подходит для первых форм и позволяет увеличивать их количество без перестройки проекта.

Допущение для этого предложения: подпроект соответствует одной самостоятельной анкете, а направление указывается в её документации. Названия двух форм ниже условные; реальные направления и состав вопросов ещё предстоит определить. Выбор редактора и способа генерации PDF остаётся открытым.

## 2. Дерево каталогов

В предлагаемой структуре все элементы обязательны, кроме отмеченных `[опционально]`. PDF-файлы показаны как примеры будущих выпусков и появляются после подготовки и утверждения формы.

```text
forms/                                  # Корень проекта
├── README.md                            # Правила работы и каталог форм
├── prompts/                             # Общие промпты проекта
│   ├── 0001.txt                         # Существующий исходный промпт
│   └── 0001_improved.txt                # Существующий улучшенный промпт
├── doc/                                 # Общая документация проекта
│   └── project-structure.md             # Настоящее предложение
├── forms/                               # Подпроекты отдельных форм
│   ├── teacher-profile/                 # Пример: анкета преподавателя
│   │   ├── prompts/
│   │   │   └── 0001-design-v1.txt
│   │   ├── docs/
│   │   │   └── README.md
│   │   ├── src/
│   │   └── output/
│   │       ├── teacher-profile-v1.0.pdf
│   │       └── drafts/                  # [опционально]
│   │           └── teacher-profile-v1.1-draft01.pdf
│   └── research-project/                # Пример: сведения об исследовании
│       ├── prompts/
│       │   └── 0001-design-v1.txt
│       ├── docs/
│       │   └── README.md
│       ├── src/
│       └── output/
│           └── research-project-v1.0.pdf
└── shared/                              # [опционально]
    ├── templates/                       # [опционально] Общие шаблоны
    └── assets/                          # [опционально] Логотипы, шрифты и др.
```

Внешнее имя `forms/` — имя текущего проекта; внутреннее `forms/` — каталог его подпроектов. Пустые каталоги можно создавать при появлении соответствующих материалов, без файлов-заглушек.

## 3. Назначение папок и документации

| Путь относительно корня | Содержимое |
| --- | --- |
| `README.md` | Назначение проекта, правила именования и выпуска, список форм со ссылками на их документацию. |
| `prompts/` | Промпты, относящиеся ко всему проекту: организация, общие требования и подходы. |
| `doc/` | Общие проектные решения и инструкции; без дублирования требований отдельных форм. |
| `forms/<form-id>/prompts/` | Промпты разработки и проверки конкретной формы. |
| `forms/<form-id>/docs/` | Требования к форме, инструкция по заполнению и сведения о выпусках. |
| `forms/<form-id>/src/` | Редактируемые исходники и локальные ресурсы, необходимые для повторного получения PDF. Формат зависит от выбранного инструмента. |
| `forms/<form-id>/output/` | Утверждённые PDF, включая предыдущие выпуски. До первого утверждения может быть пустым. |
| `forms/<form-id>/output/drafts/` | Промежуточные PDF, если их требуется сохранять. |
| `shared/` | Только материалы, используемые несколькими формами. Ресурсы одной формы остаются в её подпроекте. |

Для начала достаточно одного файла `docs/README.md` в каждом подпроекте. Его минимальное содержание:

- Название, стабильный идентификатор формы, направление, цель и целевая аудитория.
- Статус: черновик или утверждена. Ссылка на актуальный утверждённый PDF; до первого выпуска — «утверждённой версии нет».
- Список полей: идентификатор, подпись, тип данных, обязательность, ограничения и подсказка по заполнению. Например: `email | Электронная почта | строка | обязательно | адрес email`.
- Требования к заполнению, оформлению и печати либо интерактивному вводу — после уточнения режима использования.
- Инструкция получения PDF: какой исходник открыть, каким инструментом и с какими настройками экспортировать. Для общих шаблонов — ссылка на использованную версию.
- Краткая история выпусков: версия, дата, изменения, соответствующие исходники и промпты, результат проверки и сведения об утверждении.

При росте объёма требования и историю можно вынести в отдельные документы, сохранив ссылки из `docs/README.md`.

## 4. Именование и версии

**Подпроекты.** Использовать короткий стабильный идентификатор латиницей в нижнем регистре, с дефисами: `teacher-profile`, `research-project`. Полное русское название хранить в документации. Не включать номер выпуска в имя подпроекта: обновления одной анкеты остаются внутри него.

**Промпты.** Для новых файлов использовать схему `NNNN-purpose-vN.txt`:

- `0001-design-v1.txt` — первый промпт разработки;
- `0001-design-v2.txt` — его уточнённая редакция;
- `0002-review-v1.txt` — следующий промпт, посвящённый проверке.

Нумерация ведётся отдельно в каждой папке `prompts/`. Промпт, использованный для утверждённого выпуска, сохраняется; изменения записываются в следующую редакцию. Существующие `0001.txt` и `0001_improved.txt` сохраняются под текущими именами.

**Формы.** Использовать схему `<form-id>-v<major>.<minor>.pdf`:

- `teacher-profile-v1.0.pdf` — первый утверждённый выпуск;
- `teacher-profile-v1.1.pdf` — уточнения формулировок или оформления без изменения смысла собираемых данных;
- `teacher-profile-v2.0.pdf` — изменение состава или смысла полей, влияющее на сопоставимость ответов.

Черновик получает дополнительный суффикс и хранится в `output/drafts/`: `teacher-profile-v1.1-draft01.pdf`. Номер версии сам по себе не означает утверждение.

**Актуальная версия.** Единственный указатель на неё — явная ссылка в `docs/README.md`, например `../output/teacher-profile-v1.0.pdf`. Предыдущие выпуски остаются рядом под своими именами. Файлы `final-final.pdf` и отдельные копии `latest.pdf` не нужны.

**Исходники.** Для каждого утверждённого PDF сохраняется соответствующая версия исходника: `<form-id>-v1.0.<расширение>`. Если исходник состоит из нескольких файлов, они размещаются в `src/v1.0/`. Выпущенные PDF и связанные исходники не перезаписываются. Изменяемые общие ресурсы также должны иметь фиксированную версию или сохранённую копию, чтобы старый выпуск можно было воспроизвести.

## 5. Порядок работы

1. Создать подпроект с папками `prompts/`, `docs/`, `src/`, `output/` и добавить ссылку на его документацию в корневой каталог форм.
2. Описать цель, аудиторию и поля в `docs/README.md`; записать промпты разработки в `prompts/`.
3. Подготовить редактируемый исходник в `src/`, зафиксировать инструмент и настройки экспорта.
4. Получить пробный PDF. Проверить полноту полей, понятность инструкций, отображение кириллицы, переносы и поля страницы. Для интерактивной формы дополнительно проверить ввод, переход между полями и сохранение заполненных значений в выбранных программах просмотра.
5. После проверки и утверждения сохранить PDF в `output/` с номером выпуска, зафиксировать соответствующие исходники и запись в истории, обновить ссылку на актуальную версию. Порядок и ответственного за утверждение определить до первого выпуска.

## 6. Открытые вопросы

- Формы предназначены для печати, заполнения на компьютере или обоих сценариев?
- В каких программах и на каких устройствах пользователи будут открывать и заполнять PDF?
- Кто будет редактировать исходники и какими инструментами удобно пользоваться этим людям?
- Нужны ли единый фирменный стиль, несколько языков и специальные требования к доступности?
- Кто утверждает форму и по каким критериям она считается готовой?
- Как будут возвращаться и обрабатываться заполненные формы: вручную или с автоматическим извлечением данных? Где будут храниться ответы?

Предложенная структура предназначена для разработки и выпуска пустых форм. Хранилище заполненных ответов требует отдельного решения после уточнения процесса сбора данных.
